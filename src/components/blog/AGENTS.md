# Architecture rules

- Blog audio uses one useAudioPlayer hook instance (rendered once in BlogPost) shared by the Listen button and StickyAudioBar so both controls stay in sync; narrations are static MP3s at public/audio/blog/<post id>.mp3 declared by each post's `audio` entry, which src/test/blogAudio.test.ts checks against the files.
- The Fluid-interfaces demos in FluidUIDemos.tsx animate real site pieces (the blog audio bar, the shadcn Accordion, the /work and /blog cards) with their controls in the footer strip beside the caption, built from the site's Button, Switch and ToggleGroup; demo chrome is div/span (never p/h3/ul, which .blog-content restyles), they honour useReducedMotion, keep their seven prop-less named exports, must not import blogPosts.tsx (it imports them), and src/test/fluidDemos.test.tsx smoke-tests them.
- Read-along highlighting: `ReadAlongContent` (src/components/blog/ReadAlongContent.tsx) wraps every whitespace token of a post's content JSX in a span keyed `b:<top-level child index>:<word index>` (title words are `t:<i>`); `useAudioPlayer` fetches `audio.wordTimings` (public/audio/blog/<post id>.words.json, `{version, offsetSeconds, title, blocks}`, one [start, end] per token in the same order) on first play and drives `activeWord` from the audio clock. Editing a post's content JSX or re-recording a narration means regenerating that JSON (ElevenLabs Scribe timings aligned to the tokens); src/test/blogReadAlong.test.ts fails as soon as the token counts and the JSON disagree.
